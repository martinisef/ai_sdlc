## 1.0.0

### Major Changes

- 4e7d7eb: 1.0: a stability contract. The CLI commands and flags, exit codes, `--json` outputs, the config schema, the artifact and roadmap formats, the `Gate:` trailers, `sdlc hook` and the skill names do not break within 1.x; `sdlc hosted`, `sdlc webhook`, Codex and Cursor as headless agents, the dashboard API and the telemetry payload stay experimental. See [Versions and stability](https://martinisef.github.io/ai_sdlc/reference/stability) and [Upgrading from 0.x](https://martinisef.github.io/ai_sdlc/guide/upgrading). Nothing from 0.7 breaks.

  - Dashboard agent jobs use `ci.agent` or `SDLC_CI_AGENT` if set, otherwise the first of the project's `agents` whose CLI is installed, so a Cursor-only project runs `cursor-agent`. The Roadmaps page shows which agent runs.
  - A roadmap's PDF source also gets a `source.txt` when `pdftotext` is installed, for agents that cannot read PDFs.
  - Security: the dashboard shows raw HTML in artifacts as text, drops unsafe links, and sends a Content-Security-Policy; roadmap routes reject slugs that leave `changes/_roadmaps/`; `sdlc hosted` without `SDLC_HOSTED_TOKEN` listens on 127.0.0.1 only.
  - `sdlc status --metrics` is deprecated (use `sdlc metrics`) and is removed in 2.0. `--help` marks the experimental commands.
  - CI also runs on macOS.

## 0.7.0

### Minor Changes

- 8c3942c: From a technical plan to tickets. `/sdlc-roadmap` reads a technical plan (PDF, Markdown or a Google Doc), asks about what it leaves unclear and breaks it into epics and stories in `changes/_roadmaps/<slug>/roadmap.md`. A person approves it with `sdlc roadmap approve`, and `sdlc roadmap apply` creates the epics, the stories under them and the dependency links in Jira, GitHub Issues or Linear. It is idempotent, and a rerun after a failure continues where it stopped. Each story then enters the loop with `/sdlc-intent <KEY>`, and `sdlc next` suggests the first unblocked one.

  - New commands: `sdlc roadmap new|check|approve|reject|apply|status|find|list`.
  - `sdlc tracker create` accepts `--parent` and `--labels`; `sdlc tracker link BLOCKER BLOCKED` is new.
  - Config: `tracker.epic_issue_type`, `tracker.epic_link_field` (Jira Data Center) and `gates.roadmap`.
  - Dashboard: a Roadmaps view to upload a plan, answer the agent's questions, approve the breakdown and create the tickets.

## 0.5.0

### Minor Changes

- 1a7a490: Blocking review. `sdlc ci security` runs a read-only security review (injection and unsafe input, access control, data exposure and secrets) with the same finders, verifier and convergence as `sdlc ci review`. The `sdlc/review` commit status fails while an Important finding, or a security finding other than a pre-existing one, is open; it closes when the next round sees it fixed or a maintainer replies `resolved: <reason>` (`sdlc ci review-status` recomputes it). New `sdlc-security.yml` GitHub template; `sdlc-review.yml` now runs `sdlc ci review` and has a `resolve` job; GitLab and Bitbucket get security and review-status jobs, and `sdlc webhook` forwards `resolved:` replies.
- 831f22e: Human approvals scaled by risk (`risk.profile: graded`): low 0, medium 1, high 2, also for the spec and plan gates. The intent always needs a person. `sdlc approve --auto` records the approval when the tier needs nobody; a gate approved at a lower tier opens again when the change grows. `sdlc ci gate-status` counts the PR's reviews against the tier of its diff, pinned to the commit they were given on (untrusted commits invalidate them), and counts the person directing the agent as one reviewer. Only `risk.trusted_authors` get the lighter paths; an agent's approval never counts.
- f3d706d: `sdlc metrics` and the dashboard measure human time per change: approvals given by people, hours waiting for a person, review rounds and human comments (median and p95). Next to them are the guardrails: the revert rate on the default branch and incidents per change. `sdlc metrics --prs` caches rounds and comments from the forge, `--since 30d` sets the window, and `--value <name>` prints one number for a control band. A band tier with `raise_risk: { tier, hours }` is a circuit breaker: it raises the minimum risk tier for a while (`refs/sdlc/risk-floor`, read by `sdlc ci risk` and the gates) and announces it with the new `risk.raised` notification.
- feb0825: `sdlc ci nightly-review` reviews the code nobody is changing: one module per night, in rotation (`ci.nightly.modules`, else every code directory), with the review's finders and a verifier. Each Important finding becomes an intent (`origin: review`) on its own `change/review-*` branch, with a draft PR when run with `--pr`. The same finding never gets a second intent, and a night opens at most `ci.nightly.max_intents` (3). New templates: `sdlc-nightly-review.yml` (GitHub, in the regulated preset), `sdlc:nightly-review` (GitLab) and the `nightly-review` custom pipeline (Bitbucket). The same job turns the week's reverted commits into reviewer evals.
- 337abe1: `sdlc ci review` now runs one finder per pass in parallel and a verifier that votes on each finding, dropping what the code does not support and anything that is only style. Findings carry a severity (Important, Nit, Pre-existing), `file:line`, evidence and a bug class; they are posted as inline comments, with a sticky summary that starts with the counts. Depth follows the risk tier (low Quick, medium Standard, high Deep with three votes; `ci.review.depth` overrides it). Re-reviews look only at the commits since the last round, never repeat a finding, notice fixes and stop at `ci.review.max_rounds` (3). The `REVIEW.md` scaffold describes the new severities and convergence rules.
- 983c3f9: The reviewer learns from its misses. `sdlc ci capture-eval <commit> --origin incident --expect "<finding>"` turns the commit behind an incident into a reviewer eval (a patch that the review must flag as Important), and `--reverts` does the same for every reverted commit; `/sdlc-incident` runs it when a merged commit is the cause. New `output_matches` eval check, and three clean-PR evals that measure false positives. `sdlc metrics --prs` records what happened to each review finding (fixed, wrong, intentional, ignored, open; `resolved: wrong …` marks a false positive), and the agent scorecard shows the reviewer apart: clean PRs, problems caught and comment outcomes.
- 5f805eb: Risk tiers set by the change: `sdlc risk` and `sdlc ci risk` classify a change as low, medium or high from its diff (high-risk and always-human paths, weighted size, dependencies, deletions), the paths its spec and plan name, and the declared `risk:`. An optional second, agent classifier (`risk.agent_escalation`) can only raise the tier. New config: `risk.always_human_paths`, `risk.profile`, `risk.tiers`, `risk.trusted_authors`, `risk.size`, `risk.agent_escalation`.
- c865c49: New `/sdlc-explain <module>` skill: writes `docs/explainers/<module>.md` on demand with the module's architecture, invariants and risks, each with `file:line` evidence. `sdlc explainers [<path>…]` lists the explainers that cover some paths and marks the stale ones; `/sdlc-plan` cites them in a new **Explainers** section of `plan.md` and checks the plan against their invariants.
- a7cedd9: Every PR/MR description needs `## Testing`, `## Risk` (at least the tier `sdlc risk` computes) and `## How to revert` before `sdlc/gates` turns green; Spanish headings count too, and `ci.pr_sections` changes the list (`[]` turns it off). `/sdlc-ship` writes them and reminds the author that they own the change after it lands. Merge queue support: the GitHub templates run on `merge_group`, and `sdlc ci merge-queue` carries `sdlc/gates` and `sdlc/review` to the queue commit once every PR in the group has them green. New guide: "Ship and own it" (feature flags, staged release, merge queue).

## 0.4.0

### Minor Changes

- 9025457: AGENTS.md now carries the guardrails as rules (protected paths, production gate, secrets, test-lock), generated from `.sdlc/config.json`: agents without hooks (Codex, Copilot, …) were not told about them. The loop text also states the "small change outside the loop" exception. `sdlc ci evals` runs with `--agent codex|cursor` (slash prompts become the rendered skill; Codex can commit on CI runners).
- ea971af: `sdlc doctor --fix` repairs what it can, idempotently: migrates a legacy config, runs `sync`, fills missing commands from the detected stack and installs CI. What needs a person is listed as `manual` with the command to run. New doctor check `ci`: warns when no pipeline calls `sdlc`.
- 9077b99: Agent parity: `sdlc ci evals --tags a,b` runs only the evals with those tags, `sdlc ci matrix` lists the agents with credentials, and `sdlc ci scorecard <reports…>` renders the eval × agent table into `docs/reference/agent-scorecard.md`, rewriting it only when a result changed. Headless Cursor runs use `agent` (or `cursor-agent`) with `--trust`, `--mode ask` for read-only tasks and `--workspace`, and `sdlc ci bootstrap` adds `~/.local/bin` to the job's PATH after installing it.
- 588f6ff: `sdlc metrics --funnel` shows how far changes get through the loop (and the quick lane), plus minutes from `sdlc init` to the first change and gate. Opt-in telemetry: `sdlc telemetry on|off|status [--payload]`, off by default, sends anonymous daily counts only to `SDLC_TELEMETRY_URL`, respects `DO_NOT_TRACK`. New activity events `setup.init` and `setup.fix`.
- 28cb036: One-step setup: `sdlc init --preset solo|team-github|regulated` asks three questions (preset, PO, tech lead), installs the CI templates for the detected provider and prints a five-line summary. `--first-change "title"` also creates the first intent. New `sdlc ci install` copies the pipeline templates with the stack setup filled in, without overwriting. New config `gates_self_approval` (preset `solo`) lets the author approve their own spec and plan.
- e958faf: Notifications: `sdlc notify <event>` posts `gate.pending`, `gate.decided`, `spec.ready`, `review.done` and `change.merged` to Slack or any webhook (Teams, Discord with `format: generic`), mentioning whoever has to act. `sdlc ci intent-to-spec`, `gate`, `gate-status`, `review` and `jira-merged` send them when `SDLC_NOTIFY_WEBHOOK` is set; new `notify` config (`webhook_env`, `format`, `events`, `people`). Fail-open.
- 089fe66: Gates from the PR: `/approve spec` or `/reject plan <reason>` in a PR/MR comment records the gate as a commit on the change branch (`sdlc ci gate`), and `sdlc ci gate-status` sets the `sdlc/gates` commit status to require in branch protection. Roles accept forge users as `@login`. New GitHub template `sdlc-gates.yml`; GitLab and Bitbucket get `sdlc:gate` / `sdlc-gate` jobs triggered by `sdlc webhook` with `SDLC_JOB=gate`.
- 64ecf28: Quick lane for small, low-risk changes: `sdlc quick "<what>"` creates an intent with `lane: quick` (stage `quick-ready`, no spec or plan) and the new `/sdlc-quick` skill implements it with tests. The pre-push hook enforces `quick_lane` limits (default 10 code files, nothing under `risk.high_risk_paths` or `quick_lane.forbid_paths`); `sdlc quick --check` reports them and `sdlc promote` moves the change to the full loop.
- 51de87a: `sdlc next [--json]` says the one thing to do now for the person asking: approve a gate they can decide, run the next skill, wait for a named person, ship, or start a change. The session-start context and a new bar in the dashboard show the same line.
- f6f11a8: Go, .NET and Ruby on Rails stacks: `sdlc init` detects `go.mod`, a `.sln` or `.csproj` at the root, and a `Gemfile` with `config/application.rb` (before `package.json`, since these apps often carry a frontend), and fills in commands, test globs and protected paths from the new `stacks/{go,dotnet,ruby}.md` guides (en and es), including the CI setup that `sdlc ci install` uses. New `append_only_paths` config: matching files can be created but not edited once they exist, so applied migrations (`db/migrate/**`, EF Core `Migrations/`) only grow. The agent hooks and the git pre-commit enforce it.
- e60e31a: Trackers: GitHub Issues and Linear join Jira behind one `Tracker` interface (`tracker.provider: github | linear`). GitHub follows the loop with `sdlc:<stage>` labels and closes the issue on merge (`GH_TOKEN`); Linear moves workflow states over GraphQL (`LINEAR_API_KEY`, `tracker.team_key`). Keys `#123`, `owner/repo#123` and `ENG-123` are recognized. `sdlc ci jira-merged` is now `sdlc ci tracker-merged` (the old name still works) and the templates pass `GH_TOKEN` and `LINEAR_API_KEY`. The `team-github` preset defaults to GitHub Issues. New setup guides `trackers/github.md` and `trackers/linear.md`, and a Trackers reference page.
- 856394a: Editor extension for VS Code and Cursor (`ai-sdlc-<version>.vsix` on each GitHub release): the next step in the status bar, a sidebar of changes by stage with "Waiting on my gate", and commands to approve or reject, open artifacts, start a quick change, open the dashboard and run `doctor --fix`. It bundles the CLI, so nothing has to be installed. `sdlc status --json` now includes `slug` and `title`, and prints nothing when there are no changes.

### Patch Changes

- a9ee75f: `sdlc next` no longer repeats the skill name in its message. New guide "Your first change in 10 minutes" (en/es) and `scripts/demo.sh`, a scripted demo of the loop on a throwaway repo.
- 2834612: Gate skills (`/sdlc-spec`, `/sdlc-plan`, `/sdlc-build`) state that only `status` counts: an `approved_by` value never turns a draft into an approved artifact. Found by the live eval `py-spec-refuses-draft-intent`.
